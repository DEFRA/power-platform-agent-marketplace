# Project structure: shared projects and the unit test build

The default layout for plug-in and custom workflow activity (CWA) code. If the project already has a different structure, follow it. Propose this layout only for a new project, or when the human asks to restructure.

## Why shared projects

Plug-in packages (dependent assemblies) aren't supported for CWAs, so a CWA assembly can't load a separate business logic DLL at runtime. Business logic, the early-bound model and queries therefore live in **shared projects** (`.shproj` with a `.projitems` file). Each plug-in or workflow project imports them, so the shared source compiles into every assembly that registers with Dataverse.

| Project | Kind | Holds |
| --- | --- | --- |
| Business logic | Shared project | Host-independent logic classes and settings, plus [IsExternalInit.cs](../assets/IsExternalInit.cs) if the code uses `init` or records |
| Model | Shared project | The early-bound model generated by `pac modelbuilder` (see `dataverse-schema`). Never hand-edit it |
| Queries | Shared project | Repositories and queries behind the abstractions that business logic depends on |
| Plug-in and workflow projects | Class library (`net48`) | Thin entry points only. They import the shared projects |
| Shared-code assembly | Class library (`net48`) | Nothing of its own. It imports every shared project, and is used only by the unit test build |
| Unit tests | Test project (`net48`) | One project for all plug-in and workflow projects |

## Why the unit test build references the shared-code assembly

Every plug-in and workflow project compiles its own copy of the shared classes. A test project that references more than one of them would therefore see each shared class several times. That causes two problems:

- **Naming clashes**: CS0433, "the type exists in both" assemblies.
- **Misleading code coverage**: the same line is counted once for each assembly.

So the solution has a **`UnitTest` build configuration**. In it, the plug-in and workflow projects stop importing the shared projects and reference the shared-code assembly instead. The single test project then sees each shared class exactly once. Debug and Release builds are unchanged, so the assemblies that ship still carry the shared code.

Plug-in and workflow project (the shared-code assembly imports the same `.projitems` files, unconditionally):

```xml
<PropertyGroup>
  <Configurations>Debug;Release;UnitTest</Configurations>
</PropertyGroup>
<Import Project="..\Abc.BusinessLogic\Abc.BusinessLogic.projitems" Label="Shared" Condition="'$(Configuration)' != 'UnitTest'" />
<ItemGroup Condition="'$(Configuration)' == 'UnitTest'">
  <ProjectReference Include="..\Abc.SharedCode\Abc.SharedCode.csproj" />
</ItemGroup>
```

Repeat the import for each shared project. The test project references every plug-in and workflow project and the shared-code assembly.

## Working in this layout

- **Build and run unit tests in the `UnitTest` configuration** (`dotnet test -c UnitTest`). A CS0433 error in the test project usually means the test build ran in another configuration.
- **Also build the plug-in and workflow projects in Debug or Release** after changing shared code. The unit test build doesn't compile the shared source into them, so a break that only shows there (a missing SDK reference, for example) is missed otherwise.
- **List new files in the `.projitems`.** Unless it uses a wildcard, add a `Compile` entry with `$(MSBuildThisFileDirectory)` for each new file and remove the entry for each deleted one. A stale entry breaks every importing project.
- **Make shared types the entry points use `public`.** In the unit test build they're in a different assembly from the entry points.
- **Don't reference plug-in or workflow projects from shared code,** and don't put host types (`IPluginExecutionContext`, `CodeActivityContext`) in the business logic shared project.
- After moving a namespace, fix every `using` and build every importing project.
