# Project structure: shared projects and the unit test build

The preferred layout for plug-in and custom workflow activity (CWA) code. Use it for a new solution, or when the human asks to restructure. If the project already has a different structure, follow it, and move code into this layout only when the human agrees (see "Changing existing code" in the skill).

## Why shared projects

Plug-in packages (dependent assemblies) aren't supported for CWAs, so a CWA assembly can't load a separate DLL at runtime. The infrastructure, the data access code and the business logic therefore live in **shared projects** (a `.shproj` and a `.projitems` file). Each plug-in or workflow project (a *head*) imports them, so the shared source compiles into every assembly that registers with Dataverse.

| Project | Kind | Holds |
| --- | --- | --- |
| `Abc.Infrastructure` | Shared project | The scaffold, copied from the assets: the container, base classes, execution services, logging and step helpers, plus `IsExternalInit.cs` (see [infrastructure.md](infrastructure.md)) |
| `Abc.Dataverse` | Shared project | The early-bound model generated by `pac modelbuilder` (see `dataverse-schema`), the context factory, query classes and `EntityExtensions` (see [data-access.md](data-access.md)) |
| `Abc.Application` | Shared project | Application services shaped by use case, with their settings, constants and reference data. No handlers and no host types |
| `Abc.Plugins` | Class library (`net48`) | Plug-in classes and their handlers, in a folder and namespace per area (`Abc.Plugins.FieldCopying`), and one internal `PluginCompositionRoot` |
| `Abc.Workflows` | Class library (`net48`) | Activities and their handlers, arranged the same way, and one internal `WorkflowCompositionRoot` |
| `Abc.SharedCode` | Class library (`net48`) | Nothing of its own. It imports every shared project, and only the unit test build uses it |
| `Abc.UnitTests` | Test project (`net48`) | One project for every head. Its folders and namespaces mirror the code under test |

Shared projects compile together, so the compiler can't stop one from using another. Keep the direction by convention: Application may use Dataverse and Infrastructure, Dataverse may use Infrastructure, and none of them uses a head. Host types (`IPluginExecutionContext`, `CodeActivityContext`, `IWorkflowContext`) appear only in Infrastructure and the heads.

## Why the unit test build references the shared-code assembly

Every head compiles its own copy of the shared classes. A test project that references more than one head would therefore see each shared class several times. That causes two problems:

- **Naming clashes**: CS0433, "the type exists in both" assemblies.
- **Misleading code coverage**: the same line is counted once for each assembly.

So the solution has a **`UnitTest` build configuration**. In it, the heads stop importing the shared projects and reference the shared-code assembly instead. The single test project then sees each shared class exactly once. Debug and Release builds are unchanged, so the assemblies that ship still carry the shared code. `SharedSourceAssemblyTests`, in the test support assets, checks that in this build the shared types all come from one assembly, and not from the test project.

## The build files

These are the files the scaffold was verified with. In an existing solution, keep its own analyser rules and versions, and add only what is missing.

`Directory.Build.props`, at the solution root, applies to every project:

```xml
<Project>
  <PropertyGroup>
    <TargetFramework>net48</TargetFramework>
    <LangVersion>13.0</LangVersion>
    <SignAssembly>true</SignAssembly>
    <AssemblyOriginatorKeyFile>$(MSBuildThisFileDirectory)Abc.snk</AssemblyOriginatorKeyFile>
    <AbcPublicKey>REPLACE-WITH-THE-PUBLIC-KEY</AbcPublicKey>
    <EnableNETAnalyzers>true</EnableNETAnalyzers>
    <IsPackable>false</IsPackable>
    <MSTestVersion Condition="'$(MSTestVersion)' == ''">4.5.2</MSTestVersion>
    <FluentAssertionsVersion Condition="'$(FluentAssertionsVersion)' == ''">7.2.2</FluentAssertionsVersion>
  </PropertyGroup>
  <ItemGroup>
    <PackageReference Include="StyleCop.Analyzers" Version="1.1.118" PrivateAssets="all" IncludeAssets="runtime; build; native; contentfiles; analyzers; buildtransitive" />
  </ItemGroup>
</Project>
```

- Without `LangVersion`, a `net48` project compiles as C# 7.3. The version matches [stack.md](../../power-platform-standards/references/stack.md).
- The test package versions are properties so you can build against another version, for example `-p:MSTestVersion=3.11.1 -p:FluentAssertionsVersion=7.0.0`. The assets pass with both sets. Stay below FluentAssertions 8, which needs a commercial licence.
- `global.json` pins the SDK: `{ "sdk": { "version": "10.0.400", "rollForward": "latestFeature" } }`.

The root `.editorconfig` turns off StyleCop's file header rule:

```ini
root = true

[*.cs]
dotnet_diagnostic.SA1633.severity = none
```

`tests\.editorconfig` turns off the documentation rules for tests:

```ini
[*.cs]
# Tests are documented by their names and don't produce an XML documentation file.
dotnet_diagnostic.SA0001.severity = none
dotnet_diagnostic.SA1600.severity = none
```

Elsewhere, `GenerateDocumentationFile` makes StyleCop require an XML documentation comment on every public and internal type and member.

### Shared projects

Visual Studio's **Shared Project** template writes the `.shproj`, which shows the project in Solution Explorer, and the `.projitems`, which the heads import. To write them by hand, copy an existing pair and give the `.shproj` `ProjectGuid` and the `.projitems` `SharedGUID` the same new GUID. Then include every file with one wildcard. `Abc.Application.projitems`:

```xml
<?xml version="1.0" encoding="utf-8"?>
<Project xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
  <PropertyGroup>
    <MSBuildAllProjects>$(MSBuildAllProjects);$(MSBuildThisFileFullPath)</MSBuildAllProjects>
    <HasSharedItems>true</HasSharedItems>
    <SharedGUID>540157a5-8018-4cc0-89eb-352a0b235618</SharedGUID>
  </PropertyGroup>
  <PropertyGroup Label="Configuration">
    <Import_RootNamespace>Abc.Application</Import_RootNamespace>
  </PropertyGroup>
  <ItemGroup>
    <Compile Include="$(MSBuildThisFileDirectory)**\*.cs" />
  </ItemGroup>
</Project>
```

### Heads

`Abc.Plugins.csproj`. `Abc.Workflows.csproj` is the same.

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <Configurations>Debug;Release;UnitTest</Configurations>
    <GenerateDocumentationFile>true</GenerateDocumentationFile>
  </PropertyGroup>
  <Import Project="..\Abc.Infrastructure\Abc.Infrastructure.projitems" Label="Shared" Condition="'$(Configuration)' != 'UnitTest'" />
  <Import Project="..\Abc.Dataverse\Abc.Dataverse.projitems" Label="Shared" Condition="'$(Configuration)' != 'UnitTest'" />
  <Import Project="..\Abc.Application\Abc.Application.projitems" Label="Shared" Condition="'$(Configuration)' != 'UnitTest'" />
  <ItemGroup Condition="'$(Configuration)' == 'UnitTest'">
    <ProjectReference Include="..\Abc.SharedCode\Abc.SharedCode.csproj" />
  </ItemGroup>
  <ItemGroup>
    <Reference Include="System.Activities" />
    <PackageReference Include="Microsoft.CrmSdk.CoreAssemblies" Version="9.0.2.60" PrivateAssets="all" />
    <PackageReference Include="Microsoft.CrmSdk.Workflow" Version="9.0.2.60" PrivateAssets="all" />
  </ItemGroup>
  <ItemGroup>
    <InternalsVisibleTo Include="Abc.UnitTests" Key="$(AbcPublicKey)" />
  </ItemGroup>
</Project>
```

`PrivateAssets="all"` keeps the SDK assemblies out of the build output, because Dataverse supplies them.

### The shared-code assembly

`Abc.SharedCode.csproj` imports the same `.projitems` files, unconditionally:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <Configurations>UnitTest</Configurations>
    <GenerateDocumentationFile>true</GenerateDocumentationFile>
  </PropertyGroup>
  <Import Project="..\Abc.Infrastructure\Abc.Infrastructure.projitems" Label="Shared" />
  <Import Project="..\Abc.Dataverse\Abc.Dataverse.projitems" Label="Shared" />
  <Import Project="..\Abc.Application\Abc.Application.projitems" Label="Shared" />
  <ItemGroup>
    <Reference Include="System.Activities" />
    <PackageReference Include="Microsoft.CrmSdk.CoreAssemblies" Version="9.0.2.60" PrivateAssets="all" />
    <PackageReference Include="Microsoft.CrmSdk.Workflow" Version="9.0.2.60" PrivateAssets="all" />
  </ItemGroup>
  <ItemGroup>
    <InternalsVisibleTo Include="Abc.Plugins" Key="$(AbcPublicKey)" />
    <InternalsVisibleTo Include="Abc.Workflows" Key="$(AbcPublicKey)" />
  </ItemGroup>
</Project>
```

### The test project

`Abc.UnitTests.csproj` references the shared-code assembly and every head, built in the `UnitTest` configuration:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <Configurations>UnitTest</Configurations>
  </PropertyGroup>
  <ItemGroup>
    <Reference Include="System.Activities" />
    <PackageReference Include="Microsoft.CrmSdk.CoreAssemblies" Version="9.0.2.60" />
    <PackageReference Include="Microsoft.CrmSdk.Workflow" Version="9.0.2.60" />
    <PackageReference Include="Microsoft.NET.Test.Sdk" Version="18.11.0" />
    <PackageReference Include="MSTest.TestAdapter" Version="$(MSTestVersion)" />
    <PackageReference Include="MSTest.TestFramework" Version="$(MSTestVersion)" />
    <PackageReference Include="FluentAssertions" Version="$(FluentAssertionsVersion)" />
    <PackageReference Include="Moq" Version="4.20.72" />
  </ItemGroup>
  <ItemGroup>
    <ProjectReference Include="..\..\src\Abc.SharedCode\Abc.SharedCode.csproj" />
    <ProjectReference Include="..\..\src\Abc.Plugins\Abc.Plugins.csproj" SetConfiguration="Configuration=UnitTest" />
    <ProjectReference Include="..\..\src\Abc.Workflows\Abc.Workflows.csproj" SetConfiguration="Configuration=UnitTest" />
  </ItemGroup>
</Project>
```

## Signing and visibility

Dataverse accepts only strong-name-signed plug-in and CWA assemblies, so `Directory.Build.props` signs every project with one key. Create the key, and print its public key, in a Developer PowerShell for Visual Studio:

```powershell
sn -k Abc.snk
sn -p Abc.snk Abc.pub
sn -tp Abc.pub
```

Paste the public key (the long hexadecimal string, as one line) into `AbcPublicKey`, then delete `Abc.pub`. Because every assembly is signed, each `InternalsVisibleTo` needs that full key. Visibility follows the two builds:

- The shared-code assembly grants its internals to the heads. A head's `UnitTest` build then sees the same shared types as its Debug and Release builds, where the shared source is compiled in.
- Each head grants its internals to the test project, so tests can reach the internal composition root.
- Nothing grants the shared-code assembly's internals to the tests. A shared type that a test uses directly must be `public`. Keep the composition roots `internal`.

## Building and testing

```powershell
dotnet test tests\Abc.UnitTests -c UnitTest
dotnet build src\Abc.Plugins -c Release
dotnet build src\Abc.Workflows -c Release
```

- **Build and run the unit tests in the `UnitTest` configuration.** A CS0433 error in the test project usually means the test build ran in another configuration. In Visual Studio, add a `UnitTest` solution configuration that builds every project in `UnitTest`.
- **Also build every head in Debug or Release** after changing shared code. The unit test build doesn't compile the shared source into the heads, so a break that only shows there is missed otherwise. Both builds must finish without warnings.

## Working in this layout

- **New shared projects use the wildcard**, so a new file needs no entry. If an explicit `Compile` entry appears beside the wildcard (Visual Studio may add one when you add a file), delete it: a file included twice gives warning CS2002.
- **If an existing `.projitems` lists its files,** add a `Compile` entry with `$(MSBuildThisFileDirectory)` for each new file, and remove the entry for each deleted or moved one, in the same change. A stale entry breaks every head.
- **SDK-style projects (the heads, the shared-code assembly and the tests) include their files automatically.** Never list `.cs` files in them.
- **Don't reference a head from shared code,** and keep host types out of the Application and Dataverse projects.
- After moving a namespace, fix every `using`, then run the tests and build every head.
