# Anti-patterns

Patterns to avoid in acceptance automation, why, and what to do instead. Seeing one in existing code is debt to avoid repeating, not a mandate to refactor unrelated code. `test-quality-review` uses this list.

| #   | Pattern                                                                                                             | Why it hurts                                                                                                            | Instead                                                                                                                                                         |
| --- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Direct client calls (`CreateAsync`, `UpdateAsync`, `Execute`) where a ScenarioBuilder event exists                  | Bypasses the captured outputs later steps rely on. Duplicates tested setup. Hides why a record is in its state          | Find or extend the event. A direct call is acceptable for one-off reference data, but if the same snippet appears in several step files, promote it to an event |
| 2   | Setup logic built inline in UI step classes                                                                         | Blurs "how data is set up" and "how the UI is exercised". The logic is hard to find, reuse and test                     | Move reusable setup into an event in the shared test-data project                                                                                               |
| 3   | Raw Playwright (`Keyboard`, `EvaluateAsync`, `GetByText`, `WaitForAsync`) where Power Playwright has an abstraction | Brittle against UI changes that the abstraction exists to absorb                                                        | Use the typed control or page. Drop to raw Playwright only for a real gap, narrowly, with a comment saying why                                                  |
| 4   | `Task.Delay` or `Thread.Sleep` as a wait                                                                            | Too short is flaky, too long is slow, and it doesn't say what is awaited                                                | `WaitForAppIdleAsync()`, or a bounded retry around the exact condition                                                                                          |
| 5   | Assuming the dialog that a command opens                                                                            | An unexpected one, such as a validation error, gives an unclear failure                                                 | Check each possible dialog type explicitly                                                                                                                      |
| 6   | `@ignore` with no tracking                                                                                          | Coverage silently stops and the reason is lost                                                                          | Pair it with an `@issue:<id>` for the fix, and treat a long-lived one as backlog                                                                                |
| 7   | A `Then` that uses `Assert.*`, a plain `if` or a thrown exception for a business check                              | Inconsistent, less readable failures                                                                                    | FluentAssertions, always                                                                                                                                        |
| 8   | Several ungrouped assertions in one step, or in a loop                                                              | Only the first failure is reported, so each fix costs another run                                                       | Wrap them in an `AssertionScope`, with a reason on each                                                                                                         |
| 9   | An assertion-library exception in `Given` or `When`                                                                 | Blurs "setup failed" and "the behaviour is wrong". The message describes values, not why a precondition couldn't be set | A plain, domain-language exception that names the record                                                                                                        |
| 10  | One step per field                                                                                                  | Long, repetitive Gherkin and near-duplicate bindings                                                                    | Extend a table-driven step with a row                                                                                                                           |
| 11  | A null logger for builders                                                                                          | Discards what ran and what was created, exactly when a failure needs it                                                 | A real logger wired to the test output                                                                                                                          |
| 12  | Assigning roles, business units or teams in a step or event                                                         | Hides the persona's meaning. Races with other scenarios on the same user                                                | Change the persona's configuration. The pool applies it                                                                                                         |
| 13  | Two scenarios sharing a user, a record or a leftover state, or one that must run after another                      | Fails in parallel or in a different order, and the failure looks random                                                 | Each scenario takes its own user from the pool and builds its own records                                                                                       |
| 14  | Hard-coded environment values: URLs, record IDs, user names, app IDs                                                | Fails in the next, freshly deployed environment                                                                         | Take them from configuration, the package's seed data or the builder's outputs                                                                                  |
| 15  | One client instance shared across threads or scenarios                                                              | Concurrent calls corrupt each other's identity and state                                                                | A clone per scenario from the client factory                                                                                                                    |
| 16  | A feature file edited to match an implementation defect                                                             | Hides a real defect and breaks traceability                                                                             | Report the defect. See the escalation rules in [SKILL.md](../SKILL.md)                                                                                          |
| 17  | Business rules coded in the automation                                                                              | The test then agrees with the code it checks                                                                            | Assert behaviour, and raise the rule with `product-analyst`                                                                                                     |
